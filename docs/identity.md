# Tianheng Foundry - Identity

**Tagline:** Forge declared Rust architecture prose into tested Tianheng reactions.

## Thesis

Code-facing architecture context should be generated from observable law, not maintained as a
parallel essay. Foundry helps an adopter form that law without granting the agent legislative
authority.

## What It Is

Foundry is an auxiliary, portable, generative skill collection. Its workflows may write Rust
boundary and proof code after passing explicit authority and eligibility gates.

It is not a Tianheng crate, an observation dimension, a policy library, a documentation generator,
or a source of law.

## Who It Serves

The primary user is someone adopting Tianheng in their own Rust project. A mixed-language monorepo
is eligible only within its discovered Cargo workspace. A generic Rust repository is not silently
enrolled.

## Relationships

Tianheng owns the boundary DSL, observation engines, projections, and reactions. Foundry owns the
guarded transition from an adopter's declared prose claim to a reaction-proven candidate that uses
those public surfaces.

Fornax is the structural precedent for portable skill packaging and progressive disclosure.
Foundry is not a Fornax package and does not inherit Fornax's read-only identity.

All three repositories release independently. Foundry uses compatibility declarations and
fixtures, not submodules or vendored source.

## Naming

`Foundry` names formation: declared intent is heated, shaped, tested, and offered for acceptance.
It does not imply that generated output is automatically law.

Skills use lowercase kebab-case transaction names. Terms from Tianheng remain exact public
vocabulary; adopter-specific terms remain local to adopter examples.

## Voice

Instructions are direct, bounded, and operational. Reasons use forward voice and describe only the
structure their reaction protects. Historical provenance belongs in project decisions and git
history, not live generated reasons.
